# 潜客挖掘 Troubleshooting：通用产品识别、证据分级与搜索门禁

## 1. 文档目的

本文用于排查 `lead-research` 潜客研究流程中的通用问题，不绑定任何具体产品、官网、目录结构、行业或历史会话。

流程应解决四个问题：

1. 当前要研究的究竟是哪一个产品；
2. 现有信息是否足以形成产品画像、SWOT 和 ICP；
3. 应使用哪些关键词和来源寻找真实购买信号；
4. 哪些公司具备可核验的潜客证据，哪些只能排除或待验证。

核心原则：

> 先形成足以指导搜索的产品认知，再设计检索策略，最后多源搜索并核验真实线索。证据不足不等于立即停止；只有会实质改变 ICP 或检索方向的歧义才需要用户确认。

---

## 2. 正确执行链路

### 2.1 AgentOS 路由

外部 Web/API 请求先进入统一 gateway/assistant 入口。消息包含有效 `@AI员工` 时：

```text
外部请求
  → Gateway
  → MatchAtName
  → DispatchExplicitMention
  → AI 员工绑定的 Pipeline
```

潜客研究员工默认绑定 `lead-research`。没有命中有效 `@` 时，请求走普通 assistant 路径，不应由 assistant 假装成某个 AI 员工。

同一条消息存在多个员工 `@` 时，当前规则路由到第一个完整、有效的员工 mention。员工名称的部分匹配不能触发路由。

### 2.2 潜客研究四阶段

```text
产品画像与 SWOT
  → 搜索策略
  → 多源搜索与核验
  → 报告整理
```

各阶段职责必须隔离：

- 产品画像阶段：识别产品、证据分级、SWOT、竞品/替代方案、正向与负面 ICP；
- 搜索策略阶段：生成搜索假设、关键词矩阵、来源计划和接纳/淘汰规则，不执行搜索；
- 多源搜索阶段：执行查询、核验公司主体和购买信号、去重并分类；
- 报告阶段：只整理本轮已核验结果，不重新发明产品定位或潜客事实。

## 3. 常见故障模式

### 3.1 把执行工作区当成产品目录

症状：

- 用户只给产品名，模型却扫描默认工作区；
- 将工作区中最显眼的项目、可执行文件、网页或数据库当成目标产品；
- 相邻项目的功能污染产品画像。

正确规则：

- 默认工作区只是执行环境；
- 只有用户明确指定的路径才是本地搜索范围；
- 用户提供的目录也只是范围，不自动证明其中所有文件属于目标产品；
- 使用本地材料前必须通过材料自述、项目元数据、品牌、包名或一致功能链路确认归属。

### 3.2 产品事实门槛过松

症状：

- 根据同目录、相似功能或搜索排名直接认领产品身份；
- 把搜索摘要、旧报告或失败工具调用当成已验证事实；
- 将推断的定价、客户案例或商业模式写成事实。

修复原则：

- 来源只能证明其覆盖范围；
- 搜索摘要主要用于发现来源，也可记录摘要明确展示的有限信息；
- 旧助手结论只能是待验证假设；
- 失败工具调用必须保留为失败，不能在会话记忆中升级为成功。

### 3.3 产品事实门槛过严

症状：

- 找不到官网就立即要求用户补充；
- 一个网页抓取失败就停止；
- 价格、案例、部署方式等个别字段未知就拒绝形成画像；
- 要求所有结论都达到同一证据级别，导致通用研究能力退化为表单收集。

修复原则：

- 产品画像的目标是“足以推导 ICP 和检索策略”，不是完成全面尽调；
- 用户描述本身可以作为目标产品的直接主张；
- 非决定性未知应记录置信度和验证方式，不应阻断；
- 官网是强来源，但不是唯一允许的来源，也不是 `READY` 的强制条件。

### 3.4 为某个产品写特例

症状：

- 代码内置某个产品到固定官网、仓库或定位的映射；
- Prompt 出现真实产品名、历史 session、某次目录结构或某个竞品；
- 回归测试只验证某次事故，而没有验证一般不变量。

修复原则：

- 通用流程默认不内置任何产品；
- 管理员可以通过可选配置提供任意产品身份候选，但默认目录为空；
- 配置 URL 只是候选来源，不代表页面内容已经核验；
- 测试使用中性虚构产品，验证“有配置/无配置/来源冲突/网络失败”等行为类别。

### 3.5 搜索路线机械化

症状：

- 固定先扫目录、再搜官网、再找仓库；
- 重复改写近义词搜索同一问题；
- 某个搜索引擎超时后持续重试；
- 为凑齐字段或数量不断搜索。

修复原则：

- 根据输入形态和已有证据选择路线；
- 一条路线连续低收益时切换来源类型、搜索引擎或验证方式；
- 已足以支持下一阶段时及时收敛；
- 不使用固定工具调用次数作为质量标准。

### 3.6 URL 来源审计误拦截

症状：

- `web_search` 已返回合法 URL，后续 `web_fetch` 却被判定为猜测 URL；
- URL 位于较长搜索结果的后半部分时更容易出现。

根因：

- 工具审计只保存了过短的搜索结果，URL 在写入审计记录时被截断；
- URL 守卫无法在历史成功搜索结果中找到该地址。

修复原则：

- 直接 URL 只能来自用户输入、管理员可选配置或本轮真实搜索结果；
- `web_search` 审计结果应保留足够长度，支持后续 URL 来源校验；
- 仍禁止模型猜测域名、仓库账号或常见路径。

## 4. 通用证据模型

产品画像使用分级证据，而不是“有官网/无官网”的二元判断。

| 等级 | 定义 | 可支持内容 |
|---|---|---|
| A·直接证据 | 用户对目标产品的明确说明；归属明确的一方材料、源码或可验证功能 | 产品身份、明确功能、已陈述的使用场景 |
| B·交叉证据 | 两个相互独立且内容一致的可信二手来源 | 暂定产品定位、公开市场信息 |
| C·分析假设 | 根据 A/B 证据和业务机制进行的合理推演 | SWOT、ICP、机会、购买信号假设 |
| 未知 | 当前材料无法支持 | 保留缺口，不得编造 |

每条重要结论至少记录：

```text
结论
证据等级
来源定位
置信度
是否影响 ICP
后续验证方式
```

技术材料不能单独证明定价、客户案例、市场份额或商业模式。分析假设可以进入搜索策略，但必须保持“假设”标签，并设计对应的验证查询。

## 5. 产品身份与定位门禁

### 5.1 可以继续的情况

满足以下条件即可形成暂定画像并进入搜索策略：

- 目标产品身份只有一个合理解释；
- 已能说明核心价值或解决的问题；
- 已能提出至少一个合理购买方/使用场景假设；
- 未知项不会实质改变当前 ICP 和关键词方向；
- 所有推断均标注了依据和置信度。

输出：

```text
PRODUCT_PROFILE_STATUS: READY
```

`READY` 表示“足以生成可审计的搜索策略”，不表示所有商业事实已完成核验。

### 5.2 必须补问的情况

经过合理的只读调查后，仍有以下任一决定性歧义时才停止：

1. 存在两个以上同等合理的产品身份，且选择不同身份会改变目标客户；
2. 核心定位存在两个以上有证据支持的解释，且会导向不同 ICP 或搜索方向；
3. 用户没有提供最小的产品/问题线索，现有只读来源也无法得到研究起点。

停止时只询问能够解除歧义的最少信息：

```text
已确认内容：...
候选解释及影响：...
需要补充：...
INPUT_STATUS: MISSING
<!--PIPELINE_STOP-->
```

### 5.3 不得单独触发门禁的情况

- 单个网页无法访问；
- 搜索超时；
- 没有找到官网；
- 价格、案例、商业模式或部署细节未知；
- 某个 SWOT 维度只能形成低置信假设；
- 搜索结果数量少。

## 6. 输入类型与自适应路线

| 输入 | 优先动作 | 失败后的调整 |
|---|---|---|
| 详细产品描述 | 提炼用户主张，标注需验证字段 | 用一方或独立来源补充关键缺口 |
| 产品 URL | 打开页面并确认身份与能力 | 浏览器回退、搜索该 URL/品牌、独立来源 |
| 明确文件 | 读取文件，确认文件自述与目标一致 | 检查同目录少量元数据或网络来源 |
| 明确目录 | 在该范围内定位项目标识并确认归属 | 切换网络来源或对实质冲突补问 |
| 只有产品名 | 精确名称叠加功能/场景词搜索 | 切换引擎/来源；形成暂定画像或对决定性歧义补问 |
| 管理员产品候选 | 优先验证候选 URL | 候选失败不阻断，回到其他证据路线 |

不要把上述表格执行成固定顺序。路线选择取决于已有信息、来源可用性和当前最关键的未知。

## 7. SWOT、ICP 与搜索策略

### 7.1 产品画像应覆盖

- 用户任务与要解决的问题；
- 核心能力和适用场景；
- 交付、部署和集成约束；
- 已知或待验证的商业约束；
- SWOT：优势、劣势、机会、威胁；
- 竞品与替代方案：直接竞品、相邻工具、自建、人工流程、维持现状；
- 正向 ICP、负面 ICP；
- 购买方、合作伙伴、竞品、供应商、生态/媒体分类规则。

### 7.2 搜索关键词必须有推导关系

关键词应从以下内容组合生成：

```text
行业/公司类型
+ 业务问题或场景
+ 购买触发信号
+ 地区/规模/时间等用户约束
+ 来源限定词
```

关键词可以来自已确认事实，也可以来自明确标注的分析假设。每个重要假设都要有对应的验证查询和否定条件。

### 7.3 真实潜客最低证据

潜客表中的实体必须：

1. 是具名购买方，而非竞品、供应商、媒体或泛行业名单；
2. 满足用户的地区、行业、规模或时间等硬约束；
3. 有与产品问题相关的近期需求、变化或采购信号；
4. 有一个第一方强购买信号，或两个不同类别的独立来源；
5. 记录 URL、日期、来源类别、匹配依据和置信度。

只有行业匹配、公司规模或模型常识时，只能进入待验证池，不能用来凑高置信潜客数量。

## 9. 日志排查清单

### 9.1 确认是否真的路由到 AI 员工

检查：

- 是否出现 `@mention matched`；
- 命中的 employee ID/Name 是否正确；
- 是否调用 `DispatchExplicitMention`；
- `record.Pipeline` 是否为预期 Pipeline；
- 是否生成 `pipe_<pipeline>_<step>` 的进度和步骤文件。

如果没有命中：

- 检查消息是否包含完整 `@名称`；
- 检查员工的 `AtName`、Name、ID 和 mention aliases；
- 检查员工是否为 `internal_only`；
- 检查 `aeManager` 是否注册了该员工。

### 9.2 确认产品画像没有串台

检查：

- 用户实际给了哪些名称、描述、URL、目录或文件；
- 默认工作区是否被误当作产品目录；
- 本地材料如何证明归属；
- 搜索 URL 是否来自真实搜索结果；
- 旧 session 输出是否被错误当成事实；
- 失败工具调用是否被记成成功。

### 9.3 确认门禁是否过严

检查停止原因是否只是：

- 官网失败；
- 搜索超时；
- 非关键字段未知；
- 只有一个来源暂时不可用。

如果是，应调整来源路线或输出暂定结论，而不是请求用户重复提供系统能够自行分析的信息。

## 10. 回归测试矩阵

测试应使用虚构产品，覆盖行为类别，而不是复刻某个真实事故。

| 场景 | 预期 |
|---|---|
| 无管理员产品配置 | 不注入任何内置产品身份或 URL |
| 任意管理员配置命中 | 注入候选 URL，但仍要求核验 |
| 未命中配置 | 不注入其他产品信息 |
| 用户直接提供 URL | 允许抓取该 URL |
| 搜索返回 URL | 允许后续抓取该 URL |
| 模型猜测 URL | 守卫拒绝，底层抓取工具不执行 |
| 长搜索结果中的合法 URL | 审计不因通用短截断而丢失 URL |
| 默认工作区含多个项目 | 不自动认领任何项目 |
| 明确目录含相邻项目 | 只有归属明确的材料进入画像 |
| 官网失败但用户描述充分 | 输出带置信度的暂定画像并继续 |
| 两个身份会导向不同 ICP | 输出最小补问并停止 |
| 价格/案例未知 | 标记未知，不阻断 |
| 旧工具调用失败 | 会话记忆明确保留失败状态 |
| 有效 `@员工` | 路由到员工绑定 Pipeline |
| 无 `@` 或仅部分名称 | 不触发员工 |

## 11. 验收标准

- 通用代码、Prompt 和默认配置中没有具体产品身份特例；
- 外部请求命中有效 `@AI员工` 后，实际执行该员工绑定的 Pipeline；
- 默认工作区不会替代用户的目标产品；
- 产品画像区分直接证据、交叉证据、分析假设和未知；
- 网络失败或非关键字段未知不会自动触发补问；
- 只有会改变 ICP/检索方向的决定性歧义才停止；
- `READY` 表示足以生成搜索策略，而不是所有字段已核实；
- 搜索词能追溯到产品事实、ICP 或明确标注的假设；
- 只有具名购买方和可核验购买信号进入潜客表；
- 无足够证据时如实输出降级结果，不用泛行业名单凑数。

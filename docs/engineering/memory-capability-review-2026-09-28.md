# MACS 记忆与任务能力审计及提升路线

审计日期：2026-09-28；修复更新：2026-09-29。依据当前工作区源码和临时 SQLite 复现；OpenKitty 为内部代号。

## 结论与证据范围

审计时记忆服务已经具备范围隔离、候选确认、版本更正、常驻偏好、召回预算与诊断，但这些合同尚未覆盖全部历史适配器及后台数据提交路径。09-28 新增 8 个针对性检查，全部复现了与期望行为不符的结果。应先补齐确认、身份和修订一致性，再提升检索与跨任务学习。

这些检查通过 Go overlay 注入测试编译，仅使用临时数据库和合成内容；没有更改产品源码、生产数据或调用真实模型。测试中的摘要生成以确定性回调代替模型。下文保留修复前的问题与复现证据；09-29 的修复状态见下一节。本审计不是全仓质量门或整个 Agent 产品的完整审计。

## 修复前已复现的 8 项缺陷

### 1. 确认相似 key 时可能激活错误条目（优先修复）

- 复现：保存 `color` 和 `color_theme` 两条候选。用户说“确认记忆 color_theme”，工具却提交 `key=color`，服务器仍返回确认成功，`color` 变成 active。
- 根因：`internal/memory/write_evidence.go:64` 的 `explicitCandidateConfirmation` 使用子串匹配，未绑定完整目标；scope 和版本虽有检查，但不能替代用户确认目标的校验。
- 提升：把确认意图绑定精确条目、范围和版本；相似 key、否定和歧义指令必须保持候选。不要通过为某几个示例 key 增加分支解决。
- 验收：确认 A 不得激活 A 的前缀条目 B；候选更新后旧确认不能通过。

### 2. 历史适配器绕过 Agent 隔离（优先修复）

- 复现：同一用户、同一数据库中，private-agent 保存含 `quartz private-agent-only fact` 的历史事件。other-agent 经 `GetMemoryContextForTenant` 获取补充历史，随后 `Service.Recall` 的提示词出现该事实。
- 根因：`internal/memory/store.go:442` 的 FTS 查询约束 tenant/user，却没有约束 `agent_name`；`internal/app/memory_runtime.go:77` 将返回结果作为补充片段传入统一服务。统一表的 namespace 过滤不能修补适配器已经取错的内容。
- 范围：已证实同一用户不同 Agent 的历史串读；没有据此推断跨用户或跨租户泄漏。最近会话、画像、知识适配的范围也需沿调用链逐项核对。
- 提升：所有召回来源接收一致的可信身份和范围合同；有意共享必须另有明确规则。不能通过去掉用户过滤来修复召回不足。
- 验收：覆盖“历史查询 → 补充片段 → 最终提示词”，不能只测试 `memory_entries`。

### 3. 旧任务重试可能覆盖新摘要（优先修复）

- 复现：旧摘要任务先失败；新摘要任务成功写入 `new summary`；推进旧任务的重试时间并执行，结果被改回 `old summary`。
- 根因：`internal/memory/service.go:625` 的 `SaveSummary` 按 session 无条件更新，没有源消息水位或修订比较。`processing.go` 的租约令牌保护任务状态，未给摘要提交提供新旧版本约束。
- 范围：验证了队列和存储合同允许旧输入回写；没有声称每个真实模型都会生成旧结论。
- 提升：任务携带源消息区间/版本，提交时比较当前成功水位；文件摘要、数据库索引和任务完成状态的更新都要遵循同一规则。失效 worker 不得提交数据副作用。
- 验收：乱序完成、失败重试和租约被接管时，新摘要仍保持最新。

### 4. 永久失败任务会反复挤占处理名额

- 复现：前 4 个任务固定失败，第 5 个任务可正常处理。连续模拟 3 个重试时间窗口，第 5 个任务从未被尝试。
- 根因：`internal/memory/processing.go:70` 永远取最早 4 条；失败后固定等待 30 秒，`Attempts` 没有终止阈值或永久失败状态。每次调度间隔超过重试间隔时，失败旧任务可以长期占满批次。
- 提升：区分临时/永久失败，增加重试上限、递增间隔和可查看/手动重试的失败状态，保证新任务有处理机会。后台恢复还依赖后续允许的回合，可再补受宿主生命周期控制的轻量调度。
- 验收：毒任务不阻塞后续正常任务；重复失败不会无限调用模型。

### 5. 中文泛词会导致无关记忆被选入

- 复现：记忆是“我们默认把文件放到输出目录”，问题是“我们今天聊一下天文”。因共同包含“我们”，条目以 relevance=1 被选入。
- 根因：`internal/memory/service.go:745` 对中文相邻字符计分；`recall.go:119` 只要求分数大于 0。没有区分常用措辞与有辨识力的主题词。
- 提升：统一中文查询处理、抑制低信息量匹配，并校准最低相关性；使用包含常用口语的负例评测，避免仅针对本例加停用词。
- 验收：保持直接措辞的正确召回，同时降低“我们、一下、看看”等泛词引发的误召回。

### 6. 候选截断让高优先级噪声挤掉精确匹配

- 复现：保存低优先级的“星云光谱”事实，再保存 205 条高优先级、含“我们”的无关记录。问“我们来看看星云光谱”，目标条目没有进入候选；最终提示词包含 40 条无关项。
- 根因：`internal/memory/service.go:671` 的 SQL 关键词补查先按 priority 排序并截断为 200 条，真正相关性排序在截断后才做。原有基础候选池也受优先级影响。
- 提升：在候选生成阶段体现匹配质量，给高辨识度词和不同检索来源保留候选名额；再做融合排序及预算。不能只无限扩大上限。
- 验收：高频词噪声超过候选上限时，较早、低优先级但直接相关的事实仍能被找回；随后扩到万条级测延迟和命中率。

### 7. 遗忘短值会误屏蔽无关资料

- 复现：遗忘编程偏好 `Go`，再召回 `Google cloud billing procedure` 摘要，摘要被标记 retracted 并排除。
- 根因：`internal/memory/recall.go:71` 在归一化文本中逐段比较旧值哈希，没有词边界或派生来源关系；`go` 命中 `google` 开头。
- 提升：短期明确短值匹配边界；长期以记忆 ID、修订和派生关系传播更正/删除。放宽原文过滤时必须保留防复活测试。
- 验收：被遗忘事实不复活，独立且仍有效的事实也不被误删或误屏蔽。

### 8. 失败经验写入后，按用户名检索找不回来

- 复现：按宿主 `learnEvent` 的字段构造经验，包含 UserID，但 UserName 为空。该事件已进入 FTS；不带用户名能找到，按 `alice` 检索返回空。
- 根因：`internal/app/mac.go:6155` 的失败经验和相邻 Skill hint 写入复制了 UserID，遗漏 UserName；`store.go:442` 等历史检索按 UserName 过滤。`SaveMemoryEvent` 不补齐该字段。
- 范围：复现了存储/检索不一致，并核对实际写入构造；本轮未执行真实模型的完整 Generate 回合。
- 提升：先让事件写入完整继承宿主身份，再逐步让学习记录和召回使用稳定主体标识。用户名变更不应造成记忆失联，也不能以展示名合并用户。
- 验收：同一用户新会话能找回自己的失败经验，另一个用户始终不可见。

| 成功流程复用 | 已有 workflow_learner、参数槽与断言评估 | 复用现有组件，把验证成功的方法与适用范围写成可检索经验，回放仍验证关键结果 |

| 更正与遗忘完整性 | 画像、格式偏好、图谱、摘要与规范集合仍分存；原文屏蔽不等于语义删除 | 每条派生事实能追到来源，更正传播可检查；管理页显示实际生效来源 |
| 用户能处理诊断结果 | 召回记录目前主要是短 ID、版本及选择原因；没有直接跳转到相应条目的操作 | 在相同权限检查下关联当前条目并更正；条目已删除/变化时明确提示，不把正文复制进诊断日志 |
| 个人数据迁移与恢复 | 当前导出不是完整备份恢复协议，旧 JSON 的一次性 Import 也不是用户导出文件的导入功能 | 版本化导出、导入预览、冲突处理、范围绑定及恢复演练；代码快照不能代替记忆数据备份 |
| 持续质量证明 | 当前存储/召回检查不评价最终回答；已有任务黑盒框架，但本轮没有跑真实模型任务验收 | 同模型、同任务对比有/无记忆：完成率、重复犯错、纠正遵循、token、延迟和越界串读 |

图谱提取的原文校验目前证明“引用出现在用户消息中”，尚不能证明提取出的关系与原文语义一致；否定、引用他人和假设语句应加入候选质量评测。不要把模型 confidence 当作事实真伪。

## 建议实施顺序（前两步的缺陷修复已落地）

1. **先修确认与一致性**：精确候选确认、历史适配器 Agent 隔离、摘要提交水位与过期 worker 限制；补端到端回归。
2. **让已有记忆真正发挥作用**：修失败经验身份、任务重试阻塞、中文泛词和候选截断、短值误屏蔽；保留无相关内容时空召回。
3. **再提高学习与检索能力**：结构化失败/成功经验、可选语义候选、用户可纠正的来源关联。继续复用现有 Go、数据库、Tool Registry 和 workflow_learner。
4. **用真实任务判定收益**：准备至少 30 个多轮情景，覆盖记住—换种问法—纠正—重启—遗忘—跨 Agent；另取代码修复、文档生成和界面操作任务检验方法复用。通过条件应包含实际产物/断言，而非只匹配回答关键词。

统一条目、历史事件和图谱是不同层；下一步应统一它们的身份、来源和修订合同，而不是把所有数据直接合并到同一张表。

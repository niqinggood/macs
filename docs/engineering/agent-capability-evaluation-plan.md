# macs Agent 能力评估方案

制定日期：2026-10-05。源码核查基线：`5a0be4c`；README 能力对照为当前未提交的文档增补。

本方案用于回答三个问题：macs 能完成哪些实际任务，在哪些环节失败，以及下一轮开发能否改善结果。建议采用 **业务黄金集、公开专项测评、正式榜单** 三层评估。公开赛题用于外部对照，业务黄金集验证模板保真、审批、取消、幂等和崩溃恢复等 macs 的产品契约。

状态：**方案已制定，公开 benchmark 适配与模型实跑尚未完成。** 本文中的样本量、阶段安排和内部目标均为建议；官方榜单成绩须遵循对应项目的独立协议。

## 评估对象与比较口径

分别记录三种配置，结果分表展示：

1. **原生运行时**：固定模型，使用 macs 自身的模型与工具循环；关闭外部编程 Agent 委派，用于判断 macs 的编排、上下文和工具能力。
2. **完整产品配置**：启用指定 Skills、记忆、Pipeline、多 Agent 与业务工具；使用外部 Agent 时明确记录其名称、版本及费用，用于衡量用户实际获得的能力。
3. **对照或消融配置**：在支持相同模型的系统间固定模型；同一 macs 版本可分别关闭记忆或协作，观察相关能力带来的收益。其他产品只支持指定模型时，单列产品比较，记录模型差异。

每次运行冻结源码版本及工作区差异摘要、模型 ID、推理设置、提示词与 Skill 版本、工具白名单、权限模式、依赖与容器镜像、任务预算和评测器版本。公开榜单中使用统一官方 scaffold 的模型成绩，与 macs 自定义运行时成绩应注明不同轨道。

## 正式赛事与持续提交渠道

[AgentBeats](https://agentbeats.dev/) 是持续评估渠道：评测方 Green Agent 设置环境和评分，被测 Purple Agent 暴露 A2A 接口、接受任务并使用 MCP 工具；参与者打包 Docker 镜像，在隔离环境运行并展示结果。macs 需要新增薄 A2A 适配层，将任务映射到现有 AgentOS，继续复用其任务存储和执行循环。

[AgentX–AgentBeats 比赛](https://rdi.berkeley.edu/agentx-agentbeats) 的官方 Phase 2 为 2026-03-02 至 2026-06-02，截至本方案日期该届赛程已结束。其赛题和平台可作为参考，不将它描述成仍在报名的赛事。比赛公开要求包含被测 Agent 的源码仓库、A2A 兼容和说明；准备下一届或提交公开结果时须重新核对规则。

## 第一批业务黄金集

建议先固定 **30 题，每题独立运行 3 次**。这是内部业务基线，共 90 次尝试，不是任何公开 benchmark 的完整成绩。难度按单步、组合、异常恢复分层；开发样本与封存评估样本分开，修复时不针对评估题的字段原文或答案增加专用规则。

黄金集以中文业务任务为主，覆盖中英混合字段和英文工具错误，按语言分别报告。公开赛题保留官方原文；翻译或改写后的题集属于内部扩展，不能直接沿用原榜单成绩名称。

## macs 接入方式

执行链路使用：官方/内部任务环境 → 评测适配器 → AgentOS 提交 → macs 执行 → 宿主收集证据 → 官方/内部裁判 → 汇总报告。

- **任务生命周期**：复用 [AgentOS API](../agent-os-api.md) 和 [Go SDK](../../sdk/README.md)。SSE 展示进度，持久任务快照判定终态；记录中途指令、审批、取消与重启。发生 `replay_reset` 后回查快照。
- **工具环境**：文件、Shell、浏览器和桌面动作必须在赛题环境内发生。为官方环境提供窄适配器，继续接入 Tool Registry/Middleware；不能让宿主本机操作代替容器/VM 中的动作，也不能用模型端点直调代替 macs。
- **环境重置**：每次尝试独立工作区、用户身份和环境快照；需共享服务的赛题按官方方法重置。GUI 先串行运行，具备独立环境后再增加并发。
- **记忆摄入**：按任务给定的时间与会话顺序摄入历史，再询问评估问题；每个题目独立命名空间。V2 需单独实现轨迹到记忆证据的适配，不能直接把标准答案写入长期记忆。
- **裁判隔离**：答案、评估元数据、参考补丁与验收脚本留在评测侧，不放进 Agent 可读工作区。按公开协议要求开放任务材料及工具；记录网络与工具权限，不额外开放解题途径。
- **动作与产物证据**：优先检查真实数据库/页面状态、文件回读、格式解析、哈希和独立测试。模型自报完成不能单独判分。视觉或语义裁判采用固定 rubric、裁判模型/提示词版本，并人工复核争议项。

## 评分与结果分类

每个公开套件保留官方原始分数、裁判输出、样本范围和协议。内部黄金集按预先冻结的逐题契约判定完整通过；请求澄清、等待审批等只有在该题规定为目标行为时才能算通过。

| 指标 | 计算或记录方法 |
| --- | --- |
| 覆盖率 | 有有效评估结果的尝试数 / 计划尝试数；未测、环境错误单列 |
| 内部计划交付率 | 完整成功数 / 所有计划尝试数，防止静默删除失败尝试 |
| 有效尝试成功率 | 完整成功数 / 有效尝试数，按能力维度报告并给出样本量 |
| 三次全通过率 | 同一题 3 次均完整通过的题数 / 计划题数；不取三次最好成绩 |
| 部分完成 | 单独记录通过的检查点，保留官方定义，不能代替完整成功 |
| 人工介入 | 每题澄清、审批、接管次数及原因；区分必要审批和执行失败后的介入 |
| 效率与费用 | 每个维度的端到端耗时 p50/p95、模型/工具调用、Token、费用及预算耗尽情况；主任务与子任务合并记账 |
| 记忆质量 | 检索 Hit@k/MRR、回答正确率、改写问法命中、错误/遗忘项注入；检索与最终回答分表 |
| 注入影响 | 干净任务完成率、攻击条件下任务完成率、攻击成功率及未授权动作数同时报告 |
| 恢复与幂等 | 指定故障后的契约通过率、重复副作用次数、迟到 Worker 写入和终态一致性 |

将 `agent_failure`、`timeout`、`budget_exhausted`、`infrastructure_error`、`awaiting_input` 和 `skipped` 分开。所有计划尝试保留记录；公开榜单分母按其官方协议，不能自行剔除难题后沿用官方成绩名称。

费用缺少供应商 usage 或价格依据时标记未知；裁判和环境模拟器的费用单列，并另给出总评测费用。小样本同时报告成功/总数及区间估计，p95 在样本不足时仅作为诊断。

## 分阶段执行安排

### 阶段零 固定基线与检查环境

保存当前源码版本、已有工作区改动和环境清单。先完成各适配器的合成响应测试，以及超时、取消、路径与身份边界检查；确认成功和失败样例均能被裁判正确识别。

验收器先用空产物、错误字段、失败测试和已知正确样例做对照检查，确认不会将 Agent 的文字声明误记为完成。模板语义及视觉质量需要独立裁判，结构和哈希校验只承担各自可证明的部分。

仓库定义校验可使用现有命令：

```powershell
python testdata/blackbox/run_agent_harness100.py --validate-only
go test ./internal/memory -run '^TestRecallEvaluation$' -count=1 -v
```

本次会话已经确认主程序可构建，但全仓测试仍有迁移断点。逐项记录并修复；在完整质量门通过前，报告应明确所依赖的聚焦验证，不能称为全仓绿色。

### 阶段一 业务黄金集基线

完成并冻结 30 题及验收合同。先选跨能力的 5 题做环境冒烟，确认结果目录、裁判和费用统计；再运行全部题目各 3 次。采用同一主要模型，先形成 macs 原生运行时基线，再对需要 Skills、记忆和协作的题运行相应产品配置。

输出能力维度成功率、稳定性、失败类别和证据包。按失败频率与业务影响安排开发；原始结果保留，修复后使用相同输入和协议复测。

### 阶段二 公开赛题抽样诊断

建议第一组接入 LongMemEval、GAIA、Terminal-Bench 和 WebArena-Verified；每套先按能力/难度分层固定抽取 10 题，完成适配冒烟后各运行 3 次。AgentDojo 另选 10 个任务，各做干净/攻击成对运行。The Agent Company 先选 5 题验证整套企业环境，再扩展抽样；WorkArena、τ²-bench、Gaia2 和 OSWorld 2.0 按适配与资源情况推进。

抽样必须在看 macs 结果前固定 ID、抽样方法和数据版本，优先从允许开发的分区选择；不能把这种诊断分数命名为完整官方榜单成绩。上述题数是阶段目标，模型费用和资源上限在冒烟数据形成后确定。

### 阶段三 完整协议与外部对照

选与业务最相关且适配完成的套件，执行官方要求的完整分区、重复次数、时限、动作空间、资源与裁判。不同版本重新分表；Terminal-Bench 4.0 的官方资源与短预算内部测试尤其要区分。

做两组外部对照：固定模型的运行时比较，以及记录各产品默认模型的产品比较。展示费用和成功率的关系，同时说明工具、搜索服务、外部 Agent 和记忆摄入的差异。符合要求后再准备官方榜单或 AgentBeats 的结果包。

## 证据包与结果报告

现有 Runner 已有 `summary.json` 和 `summary.md`；后续扩展其统计与记录，不增加平行任务协议。每次评测的本机运行结果放在 `.local/evaluations/<run-id>/`，通用赛题与测试夹具放在 `testdata/blackbox/`。

结果包至少包括运行配置与版本摘要、任务清单、逐次尝试记录、官方原始判分、工具轨迹、产物及哈希、错误分类和按维度的汇总。完整任务成本统计与公共 benchmark 适配器属于待开发项，不能据现有进度事件假定已完成。

最终报告应回答：哪些任务可稳定交付，哪些必须人工参与，失败主要来自模型/运行时/工具/数据/环境的哪一层，修复前后的收益是多少，以及公开榜单中哪组结果可复现。评估裁判只证明所覆盖任务，不等同于任意业务或租户的全面可靠性。

## 建议内部验收目标

以下是初期试点目标，**不是行业标准或 macs 当前成绩**：

- 黄金集完整计划交付率至少 90%，三次全通过率至少 80%，并公布每个维度的分子、分母和未测项。
- 所测权限与注入场景中，观察到的未授权写入、跨用户读取和已确认写操作的重复副作用均为 0；发现一例即作为发布阻断项。
- 取消、重启和不确定写操作按各自合同验收。写入结果不确定后停止自动重放可构成正确的保护行为，但任务未交付时仍不能计为完整业务成功。
- 关键填入值和报告事实具备可核验来源；缺失、歧义和冲突按题目契约处理，未验证的数据不能被成功回执掩盖。
- 费用和时延目标通过首轮测量按业务类别确定，公开榜单遵循官方预算，不统一套用内部短任务上限。

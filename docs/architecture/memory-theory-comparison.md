# MACS（麦卡斯）记忆系统：理论、现状与常见方案对比

> 本仓库实现更新至 2026-09-29；外部方案对比沿用 2026-09-28 的资料，依据当前源码与测试整理。OpenKitty 是内部项目代号；对外产品名为 MACS。本文的“已实现”只指当前仓库代码能力，不等于经过真实用户场景或多用户端到端验收。

## 一、记忆系统要解决什么问题

Agent 的上下文窗口只能承载本轮相关信息。会话历史记录“说过什么”，任务 checkpoint 记录“执行到哪里”，RAG 文档记录“外部资料是什么”；长期记忆则应保存**以后仍可使用、归属明确、可纠正和可遗忘的用户或项目知识**。把全部聊天直接塞回提示词，会引入噪声、过期事实和隐私风险；把聊天切片放进向量库，也不会自动解决事实冲突、授权写入和删除语义。

MACS 采用的理论模型是：**先确定身份和范围，再将证据转为有状态的记忆，最后按问题受限召回**。

```text
当前对话 / 任务结果 / 会话摘要
            ↓ 证据、授权与范围检查
候选 candidate ──用户确认或可信宿主写入──→ 有效 active
                                                ↓
                                    按身份、状态、相关性与预算召回
                                                ↓
                                      Agent 本轮推理与行动
                                                ↓
                                  版本更正 / 遗忘 / 旧值屏蔽
```

这里的“记忆”是带生命周期的数据，不是新的系统指令。它不能授予工具权限，也不能证明某个文件、外部状态或任务结果此刻仍然有效。当前用户要求应优先于长期默认偏好。系统分层的运行细节见[统一记忆服务](memory-service.md)，个人版长期目标见[个人版记忆设计](personal-memory-design.md)。

## 二、MACS 当前具备的能力

| 层面 | 当前实现 | 边界 |
| --- | --- | --- |
| 存储与分层 | Go 运行时复用应用数据库；`memory_entries` 作为长期记忆的权威集合。会话工作状态、原始消息、摘要、画像、图谱、RAG 和任务 checkpoint 保持各自职责，部分内容经适配器参与召回。 | 还不是所有历史数据、画像和图谱事实的统一权威库。 |
| 身份与范围 | 宿主由可信执行身份构造 owner；分区、租户、subject、工作区和 Agent 组成命名空间。支持 user、project、session 范围；session 仅原会话可见。 | user/project 仍受当前工作区及 Agent 命名空间约束，尚无跨工作区个人总画像或团队共享。AgentOS 多用户隔离依赖认证身份，普通本地 Web 管理接口不是多用户接口。 |
| 写入与生命周期 | 类型包括偏好、事实、决策、经验；状态包括 active、candidate、deleted。生产工具的长期直接生效写入要求本轮用户原文有明确“记住”指令且负载与值完全一致；其他工具写入保留为候选。确认候选需要 key、scope 与版本；用户命令精确匹配完整 key，不能以相似前缀授权。 | 保守规则会让自然表述或改写进入候选；候选推断本身仍依赖模型遵守工具说明，尚无完整逐消息证据血缘。 |
| 更正与遗忘 | 更正和遗忘使用 `expected_version` 防止旧请求覆盖新值；遗忘清空权威条目的内容，保留删除标记，并用旧值哈希屏蔽补充召回中的原文。旧 JSON/SCM durable 值一次性导入，迁移标记防止重启后复活。 | 不会物理删除原始聊天、旧文件、画像、图谱或 RAG；语义改写可能绕过原文屏蔽，不应宣传为跨存储完全删除。 |
| 召回与注入 | 每轮生成统一、带来源的记忆上下文：有效长期条目、会话状态、允许的画像/历史/图谱和相关摘要；先做身份与状态过滤；关键词补查在候选数量截断前按匹配质量排序，再按相关性、优先级、去重与预算选择；无关长期条目不自动注入，用户可选最多 5 条常驻个人偏好。默认约 2000 估算 token，并继续经过提示注入扫描。 | 统一长期库暂无持久语义向量索引；分词/关键词召回对同义改写较弱，数据库 `LIKE` 和候选上限也限制大规模覆盖。 |
| 后台处理 | 摘要和允许的事实提取使用持久任务、内容哈希幂等、超时、最多 5 次尝试与递增等待；摘要以数据库为权威，按入队修订及有效租约校验提交，过期结果不能覆盖已接受的新修订。 | 没有独立常驻轮询器或失败任务管理界面；修订代表入队顺序，尚非完整消息血缘。 |
| 用户控制 | 本机“记忆管理”可新增、筛选、分页、确认候选、更正、遗忘和导出长期 user/project 记忆；可管理常驻偏好并查看不含正文的召回选择记录。 | HTTP 管理端点限 loopback 与同源浏览器；远程 AgentOS 用户的认证管理界面尚未建设。 |

这些能力对应的主要代码位于 [`internal/memory/`](../../internal/memory/)、[`internal/app/memory_runtime.go`](../../internal/app/memory_runtime.go) 和 [`internal/app/memory_management.go`](../../internal/app/memory_management.go)。长期格式偏好的现有权威来源仍是 `UserProfile.Constraints.artifact_format_preferences`，不能误称已经全部迁入 `memory_entries`。

## 三、常见 Agent 记忆方案如何组织

下列是可组合的架构模式，并非互斥产品类别。产品功能会变化，比较依据为文末列出的官方文档与原始论文。

| 模式与代表 | 核心做法 | 擅长 | 相对 MACS 的取舍 |
| --- | --- | --- | --- |
| 会话状态 + 跨会话存储：LangGraph | 用 thread/checkpointer 保留短期状态，用 store 保存跨会话的长期数据。 | 把任务恢复与长期知识分开，方便嵌入已有 Agent 工作流。 | 它提供存储与编排构件；具体何时写入、事实冲突、删除及身份策略仍需应用定义。MACS 已把这些策略的一部分做成领域服务。 |
| 提取事实 + 语义检索：Mem0 一类 | 从交互中写入较短记忆，配置 LLM、embedding、向量存储与检索组件，通过 add/search 等接口使用。 | 同义问法和跨会话个性化检索；集成路径直接。 | MACS 默认仅需现有 Go/数据库，部署较轻，版本与候选控制更明确；语义召回目前明显弱于采用 embedding 的典型方案。 |
| 分层上下文：MemGPT / Letta | 把有限的常驻记忆、对话上下文和按需检索的归档记忆分层，Agent 可管理其记忆块。 | 长任务中控制上下文容量，让少量重要信息持续可见。 | MACS 也区分核心与按需召回，但没有把所有长期记忆交给 Agent 自主编辑；对长期写入采取更保守的用户证据约束。 |
| 时态知识图谱：Zep / Graphiti | 从事件抽取实体和关系，记录事实有效期与来源，并结合语义、关键词、图遍历检索。 | 多实体关系、频繁变化的事实及“当时什么是真的”查询。 | MACS 有本地图谱适配，但统一权威集合仍以条目为主，没有完整时态关系与跨存储血缘；个人版若默认引入图基础设施会增加部署和治理成本。 |
| 观察—反思—经验：Generative Agents、Reflexion | 记录经历，从历史提炼高层反思，或把任务反馈写为可复用的经验以改善下一次行动。 | 长期行为一致性与从失败中学习。 | MACS 有 `experience` 类型和受限事实处理，但尚未形成“失败 → 可验证原因 → 经确认策略”的自动摩擦增强闭环；不能将普通摘要等同于可靠经验。 |

上述概括分别对应 [LangGraph 记忆文档](https://docs.langchain.com/oss/python/langgraph/add-memory)、[Mem0 开源架构](https://docs.mem0.ai/open-source/overview)、[Letta 记忆文档](https://docs.letta.com/v1-sdk/concepts/stateful-agents)、[MemGPT 论文](https://arxiv.org/abs/2310.08560)、[Graphiti 官方仓库](https://github.com/getzep/graphiti)、[Generative Agents 论文](https://arxiv.org/abs/2304.03442)及[Reflexion 论文](https://arxiv.org/abs/2303.11366)。表中“相对 MACS 的取舍”是基于这些设计与本仓库实现的分析，不是对各产品整体性能的实测排名。

## 四、同一维度上的关键差异

| 判断问题 | 只存聊天/摘要 | 向量事实库 | 分层/图谱/反思方案 | MACS 当前选择 |
| --- | --- | --- | --- | --- |
| 什么进入长期记忆？ | 常是整段或压缩后的对话。 | 提取的片段或事实。 | 常驻块、事件关系或反馈经验。 | 明确长期要求直接生效；其他工具推断先进入候选；会话状态不自动等于长期事实。 |
| 谁能看到？ | 常以会话 ID 约束。 | 依赖应用设置的过滤条件。 | 依赖 Agent、用户或图分组设计。 | 宿主绑定身份、工作区、Agent 和 scope，模型参数不能改归属。 |
| 冲突如何处理？ | 新旧摘要可能并存。 | 需要去重/更新策略。 | 可用块编辑、时间有效期或反思整合。 | 同 key/scope 的版本更正与候选确认；尚无完整语义级冲突图。 |
| 如何找回？ | 近期窗口或摘要。 | 向量/混合检索。 | 分层按需查找、图查询或经验召回。 | 关键词相关性 + 优先级 + 有界补查；改写问法仍是短板。 |
| 如何删除？ | 删除消息或摘要。 | 删除记录与索引。 | 依赖各层血缘及传播。 | 删除权威条目并阻断已知旧值的自动召回；其他存储未完全清除。 |
| 部署代价？ | 最低。 | 通常需要 embedding 与索引。 | 视方案可能需要额外服务和模型处理。 | 默认复用 Go 与应用数据库，保持个人版可运行。 |

“有向量”并不自动等于“记忆质量高”。评价还需要看错误写入率、身份串读、过期事实、纠正后的复活、删除效果、查询延迟及最终回答是否准确。相反，MACS 的治理边界较清晰，也不能代替语义检索带来的召回收益。

## 五、当前质量证据与建议演进

仓库中的 [`recall-eval.json`](../../internal/memory/testdata/recall-eval.json) 与 [`recall_eval_test.go`](../../internal/memory/recall_eval_test.go) 使用真实 SQLite 记忆服务运行 17 个合成问题（含新增的无关问题与空查询空结果检查），其中 12 个有目标。2026-09-29 复测的结果仍为 Hit@1、Hit@5 均 **9/12（75%）**，MRR **0.750**；直接措辞 **9/9** 命中，改写问法 **0/3** 命中；该夹具中的候选、遗忘及跨会话禁止内容泄漏为 **0**；无关高优先级项目条目注入已从最多 2 条降为 0 条。召回诊断解释条目为何进入或退出上下文，不代表模型实际使用了它。这些数字只衡量确定性召回，不代表模型最终回答、真实用户分布或多用户 HTTP 端到端表现。

2026-09-29 还完成了 [8 项已复现缺陷的修复](../engineering/memory-capability-review-2026-09-28.md)，覆盖精确确认、历史 Agent 隔离、摘要乱序与租约失效、任务重试阻塞、中文泛词、候选截断、遗忘短值边界和经验事件身份。这是确定性行为修复，不代表同义问法或真实模型任务成功率已经提高。

个人版宜保留现有的身份、候选、版本与删除合同，再依次增强：

1. 用真实但脱敏、获授权的失败问法扩充评测，并同时考察误召回与越界泄漏。先建立质量基线，再选择检索技术。
2. 在原有身份/状态过滤之后加入可选的语义候选层或查询扩展；保持关键词降级，避免 embedding 不可用时记忆整体失效。
3. 为候选和纠错建立逐消息证据、来源关系与可解释冲突处理；对“经验”要求可核验的任务反馈，避免把模型反思当事实。
4. 完成跨画像、图谱、摘要等派生存储的删除传播设计，并为 AgentOS 认证用户提供独立的记忆管理入口。此项完成前持续准确说明“遗忘”的边界。

这条路线保留 MACS 个人版“简单且能运行”的优势，同时补上当前最清楚的质量短板：同义改写召回和跨存储记忆治理。

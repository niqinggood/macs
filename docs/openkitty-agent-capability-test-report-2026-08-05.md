# OpenKitty Agent 能力测试与通用修复报告

- 日期：2026-08-05
- 项目目录：`E:\openkitty`
- 测试重点：Agent 的工具使用、约束遵循、失败恢复、Skill 执行和交付验收
- 测试范围：通用 30 场景语料中选取的 7 个高价值代表场景
- 最终结果：7/7 场景通过，34/34 项确定性检查通过

## 1. 测试目标

本轮测试避免以知识问答正确率作为主要指标，而是通过可复现任务验证 OpenKitty 的 Agent 能力：

1. 能否根据工具失败信息恢复，而不是停留在错误日志。
2. 能否遵守“只诊断、不修改”等用户边界。
3. 信息不足或约束冲突时，能否先澄清再执行。
4. 能否真实生成、回读和验证文件，而不是仅在回复中宣称完成。
5. 第三方依赖不可用时，能否采用等价、可验证的降级方案。
6. 能否发现并严格执行用户指定的 Skill。
7. 并发运行时，不同任务的状态、计划和证据是否相互隔离。

## 3. 测试发现的主要问题

### 3.1 工具失败被过早当成任务终止

部分可恢复失败，例如旧字符串不匹配、用户要求只读导致写工具被拒绝，曾被统一归类为终止错误。这样会阻止 Agent 根据错误提示读取当前状态并继续完成任务。

### 3.2 交付声明缺少可靠证据

文本、JSON、PPTX、XLSX 等产物可能已经被模型声称完成，但缺少宿主侧的真实回读、格式解析、页数检查、渲染覆盖或哈希核验。

### 3.3 并发任务存在全局计划状态污染

A25 在单任务运行时通过，但与其他任务并发时失败。根因是恢复逻辑读取了 Agent 级全局活动计划，另一个任务的计划状态可能错误影响当前任务的恢复判断。

### 3.4 Skill 输出格式存在“语义接近但契约不精确”问题

模型可能生成语义正确的表格内容，但遗漏 Skill 明确要求的字段前缀或枚举形式，导致结果无法被后续程序稳定消费。

### 3.5 PPT 完成状态与真实视觉验收不一致

仅生成 PPTX 或出现过一次渲染动作，不足以证明最终版本的所有页面都已渲染和检查。重新生成文件后，旧渲染结果也可能被错误沿用。

## 4. 通用修复方案

本轮修复集中在宿主运行时、契约和证据边界，没有针对某一道题写固定答案。

### 4.1 当前任务证据驱动的失败恢复

- 对明确要求的文本报告建立目标路径、必需字段、工具证据和完整回读契约。
- Provider 在任务后段失败时，仅允许基于本轮已成功读取、位于工作区内且本轮更新的真实产物生成最小恢复报告。
- 移除对 Agent 级全局活动计划的依赖，避免并发任务互相污染。
- 对路径等价、Markdown 标题修复和字段合成采用保守策略；歧义时拒绝自动修改。

实现位置：

- `text_artifact_contract.go:328`：产物路径等价判断
- `text_artifact_contract.go:370`：必需标题的保守规范化
- `text_artifact_contract.go:682`：Provider 失败后的证据绑定恢复
- `mac.go:3672`：恢复逻辑接入 Agent 主循环

### 4.2 用户约束与工具错误分层

- 用户要求只读时，写入工具仍在执行前被阻止。
- 该冲突使用结构化错误码 `user_request_policy_conflict` 返回给 Agent，使其可以继续使用只读工具完成诊断。
- 法律、安全、Hook、认证、权限和配额等硬阻断仍保持终止，未降低安全边界。

实现位置：

- `query_engine.go:1620`
- `tool_failure_boundary.go:19`
- `tool_failure_boundary.go:110`

### 4.3 产物生产与验收门禁

- 对 PPT 规格在构建前执行页数上下限检查。
- Windows 环境使用内置渲染脚本生成逐页 PNG 和联系表。
- 只有最终版本具备完整视觉覆盖时，才允许通过 PPT 完成门禁。
- PPT 重新生成后自动失效旧的渲染验收状态。
- 对普通交付任务注入只读自动验证，校验实际文件、JSON、SHA-256 和回执内容。

实现位置：

- `presentation_runtime_gate.go:957`：PPT 规格页数门禁
- `presentation_runtime_gate.go:1998`：Windows 原生渲染 QA
- `auto_verification.go:110`：宿主侧自动验证工具调用
- `mac.go:3791`：PPT QA 接入主循环
- `mac.go:3801`：通用自动验证接入主循环

### 4.4 Skill 契约的确定性处理

- 记录本轮成功写入并完整回读的 Skill 产物。
- 仅对唯一、无歧义的 Markdown 表格执行字段格式修复。
- 仅接受 Skill 契约声明的枚举值，并在原子写入后再次回读。
- 多产物、重复列、未知值、复杂表格或工作区外路径均保持 fail-closed。

实现位置：

- `explicit_skill_policy.go:240`
- `explicit_skill_policy.go:452`

### 4.5 黑盒框架强化

- 启动时确认 Gateway 报告的真实工作区与测试工作区一致。
- 区分 `completed`、`failed`、`degraded` 等真实终态。
- 校验产物数量、文件内容、JSON 字段、进度证据和最终回复。
- 交付任务重新计算 SHA-256，不信任 Agent 自报哈希。
- 支持并发场景，便于发现全局状态泄漏。

实现位置：

- `testdata/blackbox/run_common30.py:88`：工作区健康检查
- `testdata/blackbox/run_common30.py:252`：终态检查
- `testdata/blackbox/run_common30.py:333`：交付回执与 SHA-256 检查

## 6. 测试基础设施事件

原 QA 后端在一次最终运行期间返回 HTTP 402，服务错误码为 `403004`，含义为账号欠费并导致服务隔离。该错误发生在部分任务进入 Agent 工具链之前，因此不能作为 OpenKitty Agent 能力失败处理。

为继续验证 Agent 运行时，最终验收切换到配置中已经存在的 DeepSeek 备用通道，没有新增或展示任何凭据。切换后使用全新工作区重新执行全部 7 个场景并全部通过。

## 7. 安全提示与后续建议

1. 排查过程中 QA 配置内容曾进入工具输出，建议轮换该测试配置涉及的 API Key。
2. 本报告验证的是 7 个高价值代表场景，不等同于完整 30 场景全部通过。
3. 后续可在稳定的测试额度下运行完整 30 场景，并将结果接入持续集成。
4. 建议长期保留“不同模型后端 + 相同确定性检查”的测试方式，以持续区分 Agent 运行时问题和模型差异。

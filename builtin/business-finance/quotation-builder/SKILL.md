# 技术项目报价助手

把不完整的技术想法转成一份能解释、能复算、能签约前继续收敛的报价。先估范围和工作量，再形成价格；不要从“做一个平台”或“支持高并发”直接跳到金额。

## 按任务读取参考

- 任何软件开发报价，读取 [references/technical-scope.md](references/technical-scope.md)，按端、后台、集成、质量和交付工作拆 WBS。
- 任何包含人天、工期或金额的结果，读取 [references/estimation-pricing.md](references/estimation-pricing.md)，遵守估算、风险和商务公式。
- 用户要正式报价单、投标估价、方案对比或可转发提案时，再读取 [references/deliverable-template.md](references/deliverable-template.md)。
- 任何将发给客户、渠道、招标方或外部合作方的内容，都读取 [references/disclosure-policy.md](references/disclosure-policy.md)，执行最小必要披露和发送前审查。
- 用户询问方法依据、网上参考或为什么这样估时，读取 [references/sources.md](references/sources.md)。

只读本轮需要的参考；混合项目可同时读取多个。参考中的工作项是检查清单，不是默认已在范围内的功能。

## 不可跳过的报价纪律

1. **区分四个量**：工作量是人时/人日，工期是日历时间，交付成本是执行成本，客户价格是商务价格。四者不得混写。
2. **不编市场单价**：角色成本、售卖人天单价、税率、云资源价和第三方费用必须来自用户/公司价卡或本轮核验来源。缺少价卡时先给工作量和公式化金额区间，价格字段标“待提供价卡”；只有用户要求市场基准时才检索当前、同地区、同币种资料并标日期。
3. **范围与假设可定位**：每个数字必须能追溯到 WBS 行、用户事实、明确情景或计算公式。把“已确认、假设、待确认、排除项”分开。
4. **用范围表达早期不确定性**：信息越早期，区间越宽。需求未冻结时不包装成承诺性固定总价；可以给 ROM（量级估算）和进入正式报价所需条件。
5. **不漏非编码工作**：需求澄清、产品、UI/UX、架构、开发、测试、安全、性能、部署、数据迁移、项目管理、验收支持和文档按实际范围计入，不用一个笼统“开发费”掩盖。
6. **不把人数当线性加速**：工期要按依赖、关键路径、评审等待、平台审核、外部接口和上线窗口计算。增加人员会产生沟通与集成成本。
7. **不重复加风险**：若任务的悲观值已经包含某一风险，风险准备金里不要再次计算同一风险。明确准备金覆盖什么、由谁审批使用。
8. **不混淆毛利率与加成率**：目标毛利率定价使用 `价格 = 成本 / (1 - 目标毛利率)`；成本加成使用 `价格 = 成本 × (1 + 加成率)`，二选一并标明。
9. **研发结果不作无依据保证**：算法精度、模型效果、第三方审核、外部接口稳定性和峰值容量必须对应可验收指标、数据条件和验证方案；不保证尚未验证的结果。
10. **内外版本物理分离**：内部版保留 WBS、角色价卡、成本、毛利、技术路线和谈判底线；客户版只保留购买决策所需的范围、业务成果、阶段价格、验收、边界与责任。不得靠“手工删除几列”假装完成脱敏。

## 先判断报价成熟度

| 级别 | 可用输入 | 可交付结果 | 表达方式 |
|---|---|---|---|
| ROM / 量级估算 | 想法、少量页面或业务目标 | 范围树、关键假设、宽工作量区间、主要风险 | “预算参考，不是固定报价” |
| 预算级估算 | 模块清单、角色流程、主要接口、初步 NFR | 模块 WBS、三点估算、角色成本、阶段排期、预算区间 | 标置信心和待冻结项 |
| 正式报价 | 范围、原型/需求、验收、NFR、依赖、价卡和商务条件已明确 | 内部审批底稿 + 客户商务报价；详细方案按付费阶段交付 | 金额、有效期、验收和边界明确 |

如果用户只给一句需求，不要停在问卷。先给一版基于显式假设的 ROM，并只追问会显著改变架构或价格的少量问题。

## 标准工作流

### 1. 建立最小事实底稿

优先从用户文字、PRD、原型、接口文档、现有仓库和部署资料中提取：

- 交付端：小程序、H5/Web、App、管理后台、开放 API、数据/算法服务；
- 用户与角色：外部用户、运营、审核、财务、客服、管理员、合作方；
- 核心流程：每个角色要完成的业务闭环和异常分支；
- 数据与集成：存量数据、迁移、支付/登录/地图/短信/ERP/CRM/硬件等外部依赖；
- 非功能目标：安全、隐私、性能、容量、可用性、审计、备份、RTO/RPO、合规和地域；
- 交付约束：目标日期、团队、技术栈、是否复用、环境、源码/IP、质保和运维；
- 商务参数：币种、含税/未税、内部成本价卡或售卖价卡、毛利/加成、付款节点、报价有效期。

列出会改变技术路线或报价的待确认项。无法及时确认时，给 A/B 情景，不悄悄选择更贵或更便宜的一档。

### 2. 形成技术范围和 WBS

按 [references/technical-scope.md](references/technical-scope.md) 拆成可验收交付物。至少分开：

- 产品/设计与公共工程；
- 各客户端；
- 业务后台与管理后台；
- 数据、外部集成和迁移；
- 测试、安全、性能、发布和交接；
- 算法/AI 的数据、实验、评估、服务化和持续运营工作。

一个 WBS 行应能说明“交付什么、谁做、完成标准是什么”。超过一个迭代或同时混合多个角色的行继续拆分。

### 3. 把并发目标变成工作负载

“并发用户”不等于 QPS/TPS。涉及并发、高可用或大数据量时，必须至少记录：

- 注册用户、DAU/MAU、同时在线/活跃会话；
- 每类关键操作的峰值 QPS/TPS、读写比、请求/响应大小和突发系数；
- P95/P99 延迟、错误率、可用性、数据一致性、保留期和增长；
- 单区域/多区域、容灾、RTO/RPO、降级、限流、重试和第三方限额；
- 生产相似环境中的基准/负载/压力/耐久测试与观测指标。

只有用户行为数据足够时才用 `QPS ≈ 活跃用户 × 每用户每分钟操作数 ÷ 60 × 峰值系数` 做情景推导，并明确它是推导值，不是测量值。最终容量需要压测或历史基线验证。

### 4. 单独估算法与 AI 工作

先区分：调用现成 API、部署现成模型、微调/检索增强、训练自有模型、算法研究、通用算法框架。分别估算数据权利与质量、标注、基线、实验轮次、离线指标、在线验收、训练资源、推理吞吐/延迟、服务化、监控、回滚、再训练和人工复核。

研究型目标先报价“可行性 Spike/PoC + 决策门”，再决定产品化阶段。模型指标必须写清数据集、切分、基线、阈值和验收方式；不得只写“准确率高”。

### 5. 估工作量、工期与价格

- 首选自下而上的 WBS 三点估算；有同类历史实际数据时用类比校准。
- 需求较完整且组织有稳定的功能规模生产率时，可用 COSMIC/功能点交叉验证。
- COCOMO II 只作为有规模数据和已校准参数时的辅助检查，不用拍脑袋 KLOC 生成正式报价。
- 先算每行 O/M/P 与角色人日，再聚合到模块、阶段和角色；工期另按依赖与可并行度排。
- 再加入一次性外采/云/GPU/许可证成本、明确的间接成本、风险准备金和目标毛利或加成，最后处理折扣和税。

金额较多时，在技能运行时目录使用确定性计算器：

```text
python scripts/calculate_quote.py quote-input.json --format markdown
python scripts/calculate_quote.py quote-input.json --format json
python scripts/calculate_quote.py --example
```

输入只能使用已确认值或已标注的情景假设。计算器负责 PERT、角色成本、P80/P95 近似、间接成本、准备金、毛利、折扣、取整和税；它不替代范围判断，也不证明任务相互独立。字段说明见 [references/estimation-pricing.md](references/estimation-pricing.md)。

计算器的 JSON 和 Markdown 都是**内部核算输出**，不得直接转发客户。对外版本必须按披露规则重新编排，而不是复制内部表后隐藏列。

### 6. 建立三层披露包

按 [references/disclosure-policy.md](references/disclosure-policy.md) 生成彼此独立的文件或消息：

1. **内部测算版**：完整 WBS、O/M/P、角色人日与价卡、成本/毛利、技术判断、风险、红线和折扣授权；
2. **客户商务版**：项目目标、模块级范围、可验收成果、阶段总价、工期、客户责任、排除项、付款与变更；不含实现蓝图；
3. **付费方案版**：客户需要详细原型、架构、接口、数据模型、容量模型、算法路线或任务计划时，先把“方案定义/技术尽调”作为有价格、有周期、有验收的阶段。若用户同意，可约定后续签实施合同时抵扣该阶段费用。

未说明受众时，聊天中的详细估算视为内部讨论；任何“可转发、给客户、投标文件”默认使用客户商务版。外发前运行：

```text
python scripts/review_client_quote.py client-quote.md --strict
```

发现内部经济数据、API 路径、数据模型、详细任务清单或技术选型时，停止发送并重写；不要只加“保密”水印后继续泄露。

### 7. 交付可决策的结果

内部讨论默认给出：

1. 报价级别、币种、含税状态和有效边界；
2. 已确认事实、关键假设、待确认项和排除项；
3. 按模块/阶段的 WBS、人日与内部价格依据；
4. 角色投入、关键路径和日历工期；
5. 一次性项目费、周期性费用和按量费用分列；
6. 风险、可选项、客户责任、验收和变更机制；
7. 最终总价或预算区间，以及从数字到公式的复算路径。

客户商务版改为“模块/阶段 + 业务成果 + 验收 + 阶段总价”，不得带逐项 WBS、人日、角色单价、成本、毛利、接口路径、表结构、算法权重、部署拓扑或可直接照做的实施步骤。不要为了展示销售技巧强制生成“基础/标准/旗舰”三档。只有范围确实可分层时才给方案，并逐项说明增减的成果、NFR 和责任边界。用户明确要求文件时，再按 [references/deliverable-template.md](references/deliverable-template.md) 输出到 `.openkitty/storage/`。

## 完成前复核

- [ ] 金额、币种、税、单位、人时/人日口径一致；
- [ ] 总人日能由 WBS 相加得到，报价能由价卡和公式复算；
- [ ] 小程序/H5/后台/接口没有把公共后端重复计算，也没有遗漏各端差异；
- [ ] 并发目标已经转为工作负载和测试范围，或明确标为待确认；
- [ ] 算法研发、产品化、训练/推理资源和持续运营没有混成一个“算法费”；
- [ ] 测试、部署、项目管理、文档、验收、质保和外部等待已按实际范围处理；
- [ ] 悲观估算与风险准备金没有重复覆盖同一风险；
- [ ] 周期性/按量成本没有混入一次性开发总价；
- [ ] 所有假设、排除项、客户责任、付款节点和变更触发条件清楚；
- [ ] 早期估算没有写成保证，正式报价具备验收边界。
- [ ] 内部测算版、客户商务版和付费方案版文件名与存放位置分开；客户版没有内部成本、角色价卡、毛利或谈判底线；
- [ ] 客户版没有 API 清单、表结构/字段、源码结构、算法/Prompt 细节、基础设施拓扑或逐任务实施清单；
- [ ] 同一对外包中的总价、税口径、优惠、工期和付款金额相互一致；
- [ ] 已对客户版运行 `review_client_quote.py --strict`，阻断项为零，警告均有明确保留理由。

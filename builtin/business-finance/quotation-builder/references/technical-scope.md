# 技术范围拆分

本参考用于把需求拆成可验收的 WBS。只选择实际命中的工作项；不要因为清单中存在就默认收费，也不要把同一公共能力在多个端重复计算。

## WBS 行的最小结构

每一行至少包含：

| 字段 | 要求 |
|---|---|
| ID / 工作流 | 能稳定引用，例如 `MP-AUTH-01` |
| 交付物 | 页面、接口、服务、数据集、模型、测试报告或文档 |
| 范围说明 | 正常流、异常流、角色、数据和边界 |
| 验收条件 | 可观察、可测试；避免“体验良好”“性能高” |
| 责任角色 | 产品、设计、前端、后端、算法、QA、DevOps 等 |
| 依赖 | 原型、客户数据、第三方账号、前置模块、审核或环境 |
| O/M/P | 最乐观、最可能、悲观的人日；同一口径 |
| 状态 | 已确认、假设、待确认、可选、排除 |

同一 WBS 行如果跨多个主要角色、包含多个独立验收结果或持续时间超过一个迭代，应继续拆分。

## 公共工程与交付管理

按实际需要检查：

- 需求梳理、用户故事、原型、视觉规范、设计评审；
- 架构方案、技术选型、仓库/分支、代码规范、基础脚手架；
- 多环境配置、密钥管理、CI/CD、制品、灰度和回滚；
- 项目管理、例会、风险/问题跟踪、演示、UAT 支持；
- 测试计划、单元/集成/E2E、兼容、安全和性能测试；
- 培训、操作手册、API 文档、部署手册、源码和知识转移；
- 质保范围、缺陷等级、响应窗口、上线陪跑和后续运维。

管理和质量工作应从真实活动估算，不能机械地套一个固定百分比。

## 小程序

先确认平台和实现路线：微信/支付宝/抖音等平台原生，还是 Taro、uni-app 等跨端方案；已有 H5 或组件能否复用。跨端能复用业务逻辑，不代表登录、支付、审核、隐私、能力组件和兼容测试可以完全复用。

### 功能与平台工作

- 页面、组件、导航、状态管理、错误/空态、离线与弱网体验；
- 手机号/平台登录、账号绑定、授权与注销；
- 支付、退款、订单、订阅消息、客服、地图/定位、扫码、上传、分享；
- 隐私清单、用户协议入口、权限说明、内容安全与平台合规；
- 开发者/体验/正式环境、域名白名单、证书、包体和分包；
- 真机和机型兼容、体验版/UAT、提交审核、驳回整改与发布。

### 主要成本驱动

- 平台数量与差异化能力；
- 页面不是简单计数：复杂交互、富媒体、实时通信、图表、地图和设备能力会改变工作量；
- 登录与既有账号体系是否打通；
- 支付/退款/分账、内容审核、实名或行业资质；
- 客户能否及时提供主体、账号、证书、域名和审核材料；
- 是否要求多个主题、国际化、无障碍、埋点或 A/B 实验。

平台审核等待是工期依赖，不等同于开发人日。无法控制的审核结果不能承诺通过日期。

## H5 / Web / PWA

### 范围检查

- 路由、页面模板、组件、表单、校验、上传下载和数据可视化；
- 响应式断点、目标设备、浏览器矩阵、微信/企业微信 WebView；
- OAuth/单点登录、微信内支付、深链、分享和回跳；
- SEO、SSR/SSG、站点地图、结构化数据、多语言；
- PWA、离线缓存、推送、安装和版本更新；
- 前端性能预算、首屏、资源压缩、缓存和监控；
- 可访问性、隐私同意、埋点和营销归因。

### 主要成本驱动

区分展示站、表单型业务、复杂工作台和实时协作应用。相同页面数下，状态数量、交互复杂度、权限、数据量和实时性可能导致完全不同的工作量。

## 管理后台

“后台”至少要区分管理前端与业务后端。管理后台不能只按 CRUD 页数估算，先识别：

- 组织、租户、用户、角色、菜单、字段/数据范围权限；
- 业务对象、状态机、审批、驳回、撤回、转交、批处理；
- 列表/详情/编辑、复杂筛选、导入导出、打印、附件；
- 运营配置、内容、商品、订单、客户、活动或规则管理；
- 仪表盘、报表口径、钻取、异步导出和数据权限；
- 审计日志、敏感操作二次确认、风控和客服工具；
- 多租户隔离、品牌配置、国际化和时区。

把“字段数量、状态数量、权限维度、审批分支、报表口径、批量规模”写入验收条件，避免只写“用户管理一个模块”。

## 业务后端、API 与服务

### 业务能力

- 领域实体、状态机、规则、幂等、事务和一致性；
- API 契约、版本、鉴权、权限、限流、错误码和文档；
- 搜索、文件/对象存储、通知、定时任务、消息队列和实时推送；
- 支付、账务、退款、对账、结算或分账；
- 工作流、规则引擎、异步任务和人工补偿；
- 缓存、索引、分区、归档和冷热数据；
- 多租户、区域、语言、币种和时区。

### 外部集成

每个第三方系统单独记录：接口数量和方向、认证、沙箱、限额、回调、幂等、重试、对账、错误处理、联调窗口、监控、SLA 和责任人。只有接口文档不等于联调条件已经具备。

### 数据迁移

分开估算数据盘点、映射、清洗、脱敏、转换脚本、校验、演练、停机窗口、增量同步、回滚和最终签收。迁移价格依赖数据质量和数量，不宜仅按表数量报价。

## 并发、容量与可靠性

先建立工作负载，不从注册用户数直接选架构。

### 输入基线

| 维度 | 需要的事实或情景 |
|---|---|
| 用户 | 注册量、DAU/MAU、同时在线、活跃会话、地理分布 |
| 流量 | 关键操作 QPS/TPS、读写比、峰值/平均、突发持续时间、重试 |
| 数据 | 初始量、日增量、保留期、对象大小、查询和热点模式 |
| 性能 | P50/P95/P99 延迟、超时、错误率、批任务窗口 |
| 可用性 | SLO、单/多区域、容灾等级、RTO/RPO、维护窗口 |
| 依赖 | 第三方限额、数据库/缓存/队列、网络和对象存储 |
| 增长 | 上线峰值、营销事件、半年/一年增长情景 |

### 可能增加的交付物

- 可观测性：指标、日志、追踪、仪表板和告警；
- 缓存、队列、连接池、索引、读写分离、分区/分片；
- 限流、配额、熔断、超时、退避重试、幂等和负载卸载；
- 水平扩展、自动扩缩、无状态化、会话和分布式一致性；
- 多可用区/多区域、备份恢复、容灾演练和降级；
- 生产相似测试环境、脚本/数据、基准/负载/压力/峰值/耐久测试；
- 容量模型、瓶颈分析、优化复测和最终报告。

将“达到某个 QPS”绑定到硬件/云规格、数据集、流量混合、响应大小、测试时长、延迟/错误阈值和测试环境；否则无法验收。云资源费用与实现/压测人日分开报价。

## 算法、AI 与算法框架

先选交付类型，避免把不同风险的工作混成一项。

| 类型 | 典型范围 | 关键未知 |
|---|---|---|
| 现成 API 集成 | 提示/参数、调用、降级、内容安全、成本监控 | 第三方能力、限额、单次成本、数据边界 |
| 现成模型部署 | 模型选型、容器、推理 API、压测、监控 | 硬件、吞吐、延迟、许可证 |
| RAG / 微调 | 数据整理、检索/训练、评估、版本和上线 | 数据质量、指标、实验轮次、模型变化 |
| 自研模型/算法 | 基线、特征、训练、消融、评估、迭代 | 可行性、数据/标签、效果上限 |
| 算法框架/平台 | 组件接口、配置、插件、流水线、实验追踪、SDK | 通用性边界、兼容矩阵、扩展性和维护 |
| 生产 MLOps | 数据/训练/验证/部署流水线、注册、监控、回滚/再训练 | 自动化等级、漂移、审批、审计和运营责任 |

### 必拆工作流

1. 问题定义与可验收指标；
2. 数据获取权利、盘点、质量、标注、切分与版本；
3. 规则/简单模型基线和可行性 Spike；
4. 特征、训练或算法实现、实验设计和实验轮次；
5. 离线评估、鲁棒性、分群/切片、公平/安全和人工评审；
6. 训练流水线、复现、制品、模型/算法版本；
7. 在线/批量推理、资源选型、压测、降级与缓存；
8. 应用集成、A/B 或灰度、可观测性、漂移和反馈闭环；
9. 文档、知识转移、运营、再训练和持续资源费用。

训练资源、标注、第三方模型/API 和推理资源分列为一次性、周期性或按量成本。效果未知时采用阶段报价：`Spike/PoC → 指标评审/Go-No-Go → 产品化 → 运营`。

## 既有系统改造、迁移与接手

新增功能之前检查：

- 代码、文档、测试、部署和实际环境是否可访问；
- 技术栈、版本、依赖、许可证、安全漏洞和维护状态；
- 架构边界、数据库、外部接口和历史数据质量；
- 回归范围、兼容版本、停机/灰度/回滚和双写；
- 原供应商支持、知识转移和隐性手工流程。

信息不足时单列“接手审计/技术尽调/Spike”，不要把未知遗留风险塞进普通功能人日，也不要承诺原系统行为全部保持不变。

## 多端复用与防重复计算

- 公共业务后端、数据库、鉴权和通用设计系统只计算一次；
- 每个端单独计算 UI、平台适配、端能力、兼容测试和发布；
- 跨端框架的复用比例必须来自原型/现有组件或历史数据，不能固定假设；
- 同一个验收用例可跨端复用测试设计，但执行和缺陷修复仍可能按端发生；
- 公共需求/架构/项目管理不能既作为独立 WBS，又以模糊百分比重复叠加。

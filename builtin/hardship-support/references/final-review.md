# 最终交付复核

用于复杂困难帮扶任务交付前的 Skill 内部复核。候选草案可能同时包含正确计算和看似专业的编造，应逐项核对并直接修订；不要把草案的完整、排版或自信语气当作可信依据。

## 0. 硬性复核方法

先在内部建立四张白名单：

1. **用户事实**：用户原话明确给出的对象、金额、日期、状态和限制。
2. **材料或来源事实**：用户材料能证明的内容，以及本轮实际打开且适用的官方来源。
3. **必要算术结果**：只保留完成用户明确计算所必需、并由脚本复核的结果，不顺手推导月化、概率、区间、期限或建议金额。
4. **用户要求的交付标签**：例如用户明确要求“今天 / 7 天 / 30 天”时，这些标题可以保留，但不能借标题新增付款日程。

白名单以外的具体数字、电话样式、客服号段、期限、比例、区间、机构专名和产品条件必须删除。写成“待核实”“仅供参考”“未联网核验”或放进风险提示、脚本、表格和括号里也不例外。通用对象名称（发卡机构、贷款机构、合同约定渠道、当地主管部门）可以使用。

候选草案中的每句话都要重新证明。发现一句话一半可保留、一半无依据时，只保留可证明的部分；不要因为删除后显得不够专业而补入另一个数字或惯例。

## 1. 事实与证据

- 检查答案中的每个金额、日期、期限、状态、机构名称、规则和程序判断，确保能追溯到用户陈述、用户材料、成功读取的文件或本轮实际打开的官方来源。
- 用户没有提供、材料无法证明或本轮没有核验的信息继续写成“待核实”或明确的条件项，不把沉默改写成“无”“0”“默认正常”“已经处理”。
- 用户陈述可以作为本轮规划事实，但不能写成已经被机构、法院、银行、税务机关或其他第三方正式确认。
- 分析建议、情景假设和已发生事实要分开表达，不能让建议看起来像已经生效的安排。

## 2. 联网与当前信息

- 用户禁止联网或本轮没有取得可用网页证据时，删除模型记忆补出的现行热线号码、机构名单、政策或法律数字、利率边界、产品条件、办理期限、资格条件和具体入口名称。
- “未联网核验”“仅供参考”“可能有变化”不能使未经核验的具体名称或数字变成可交付信息；无法核验时改写为需要确认的字段和查验方法。
- 用户允许联网时，只使用本轮实际打开且与地区、日期、对象匹配的官方来源。搜索摘要、广告、中介话术和记忆不能替代原始页面。
- 未联网时，热线和客服号即使只写为部分号段、星号掩码或“待核验渠道”也必须删除；只告诉用户从合同、账单、已安装的官方应用或自行确认的官方页面寻找入口。

## 3. 现金流与付款表达

- 用户给出收入、必要支出和固定还款时，必须保留两条独立算式：`收入 - 必要支出 = 还债前可用额`，以及 `还债前可用额 - 固定还款 = 扣除固定还款后余额`。
- 清楚区分“按月测算的余额”和“当前账户里实际可支配的现金”。当前现金未知时必须继续保持未知。
- 不把月度测算写成“今天就留出”“到期前保证付入”“本月一定支付”“已经锁定”或“设置自动扣款”；除非这些动作和金额是用户已经明确确认的事实。
- 扣除固定还款后的余额是尚待共同分配的资金池，不凭空增加安全垫、付款区间、整数拆分或向某一债权人的具体付款额。
- 用户给出的最低还款等义务数字可以进入月度基线，但在当前现金、到期日和账单状态未知时，不能把它改写成“先维持”“先保证”“按现有金额履行”“留出”“转入”或其他付款动作。
- 多步金额只引用成功运行现金流脚本所得的结果；不要向用户暴露内部路径、命令失败、调试过程或工具日志。

## 4. 债务排序、协商与话术

- “优先级”首先表示先核实、先联系、先保存证据或先准备材料，不自动表示先向谁付款。
- 不补造协商成功率、减免阈值、费率、分期期数、协商期限、每期金额、宽限天数或机构惯例。
- 在主要债务的合同、账单、到期状态和书面方案尚未明确前，不替次级债务、朋友借款或其他对象制定固定付款日程。
- 用户只说“几天后到期”时，原样保留为待核实的紧迫节点；没有合同或账单时，不擅自改称“当期还款日”“整体到期日”，也不据此承诺付款。
- 用户点名要求联系谁，就为每个对象分别给出第一人称、可直接发送的完整话术。话术可以请求核对、说明困难、索取书面方案或约定再次联系，但不能承诺尚未确认的付款金额、日期或结果。
- 协商话术不得补入客服号段、机构回复时限、用户承诺回复时限、固定分期目标、亲友月付区间或开始月份。可以留空让用户在取得书面方案后填写，但不能把空白旁边的示例数字随后变成行动建议。
- 若候选草案遗漏用户要求的计算、排序、话术或行动步骤，复核时直接补齐，但新增内容仍必须遵守事实边界。

## 5. 法律、催收、贷款与程序边界

- “用户没有拿到纸质法院材料”不能推出“没有诉讼、仲裁、执行或电子送达”；只能写明当前材料范围，并提示核验电子通知、官方渠道和送达信息。
- 不把陌生电话、收费、对公账户、个人账户、验证码或上门行为写成绝对的真假规则。基于可见证据给风险信号和核验动作，不做未经证实的定性。
- 不保证停催、停息、挂账、减免、贷款获批、征信恢复、救助获批、调解成功或任何程序结果。
- 不声称最低还款能够“维持征信基本盘”“稳住账户状态”或必然避免新的逾期、计息、催收和程序后果；这些都取决于合同、账单、付款状态和当前规则。
- 涉及精确法律结论时，先保留事实、证据、期限和争议点，再衔接法律能力；不能用一句“咨询专业人士”替代当前能够完成的整理和行动导航。

## 6. 完整性与呈现

- 最终答案应直接回答用户真正要求的内容：必要计算、处理顺序、今天能做的动作、需要准备的材料、可直接使用的话术，以及依赖哪些未知信息。
- 删除“我来复核”“上游答案”“以下是修改后版本”等审查者前言，直接进入交付内容。
- 删除内部 Skill 名、reference 文件名、运行时目录、工具契约、测试口径、脚本命令和工具日志。
- 保留有帮助的解释，但不要用大段免责文字冲淡行动建议，也不要因为谨慎而退化成只让用户另找专家。

## 7. Skill 内复核工作流

1. 对候选答案逐项应用本清单，先修事实、数字、程序状态和付款表达，再检查是否完整回答用户任务。
2. 运行环境能够安全传入文本时，可选使用 `scripts/review_answer.py --answer-file ...` 或 `--answer-stdin` 辅助检查。脚本 JSON 只作为内部 lint 结果，不是另一套专业规则。
3. 脚本返回 `review_status=fail` 时修订相关问题；脚本不可用、运行失败或没有安全传入方式时，继续按本清单人工复核，不调用宿主专用工具，也不阻断交付。
4. 即使脚本通过，仍要完成用户要求的计算、顺序、话术和行动，不能退化成免责说明。
5. 不向用户展示候选文件、校验 JSON、内部路径、命令或工具过程。

交付前做最后一次扫描：是否出现了无来源的数字或机构名；是否把未知写成已知；是否把建议写成承诺；是否把处理顺序误写成付款指令；是否遗漏用户明确点名要求的计算、对象或话术。发现任一问题时，直接改写后再交付。
